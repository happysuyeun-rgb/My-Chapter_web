PROLOGUE

이 책을 시작하기 전에

코딩을 배우는 책이 아니라, 내 웹사이트 하나를 완성하는 책입니다

처음 AI로 웹사이트를 만들 수 있다는 이야기를 들었을 때 저도 궁금했습니다.

“정말 코딩을 몰라도 가능한가?”

ChatGPT에게 몇 마디 입력하면 사이트가 만들어지고, AI가 코드까지 작성해준다는 이야기는 많았습니다. 그런데 직접 해보니 반은 맞고 반은 달랐습니다.

AI는 생각보다 많은 것을 만들어줄 수 있었습니다. 화면도 만들고, 코드도 작성하고, 오류도 찾아주고, 모바일 화면까지 수정해줬습니다. 하지만 그렇다고 아무 생각 없이 “포트폴리오 하나 만들어줘”라고 말하면 좋은 포트폴리오가 완성되는 것은 아니었습니다.

무엇을 보여줄지 결정해야 했고, 내 경험을 정리해야 했고, 프로젝트를 골라야 했습니다. AI가 만든 디자인 중 무엇을 남길지도 판단해야 했고, 원하는 결과가 나오지 않으면 다시 설명해야 했습니다.

결국 중요한 건 코드를 직접 작성하는 능력만이 아니었습니다.

내가 무엇을 만들고 싶은지 정의하고, 결과를 보고 판단하는 능력이 훨씬 중요했습니다.

저도 개발자가 아닙니다

저는 웹·모바일 서비스를 기획하는 일을 해왔습니다. 서비스 구조를 만들고, IA를 설계하고, 정책을 정리하고, 사용자 흐름과 화면을 정의하는 것이 제 일이었습니다. 제가 기획한 내용을 디자이너와 개발자에게 전달하고 실제 서비스가 만들어지는 과정을 함께하는 역할에 더 가까웠습니다.

직접 코드를 작성하는 사람은 아니었습니다.

그러다 생성형 AI와 AI 코딩 도구를 사용하기 시작하면서 제 작업 범위가 조금씩 달라졌습니다. 처음에는 문장을 정리하는 데 AI를 사용했습니다. 그다음에는 사이트 구조를 같이 고민했습니다. 화면 디자인도 만들어봤습니다. 그리고 어느 순간에는 제가 기획한 화면을 AI에게 구현시키고 있었습니다.

이후에는 개인 포트폴리오뿐 아니라 랜딩페이지와 기업용 홈페이지, 개인 웹서비스 형태까지 직접 만들어보게 됐습니다.

그 과정에서 느낀 것이 있습니다.

개발자가 아니어도 웹사이트를 직접 완성할 수 있는 범위가 이전보다 훨씬 넓어졌다는 것.

그리고 동시에,

AI가 있다고 해서 기획과 판단이 필요 없어지는 것은 아니라는 것.

이 책은 그 두 가지 경험에서 시작했습니다.

이 책의 목표는 아주 구체적입니다

이 책을 다 읽었을 때 “AI로 웹사이트를 만들 수 있구나” 정도로 끝내고 싶지 않습니다.

최종적으로 여러분에게는 실제로 접속할 수 있는 자신의 포트폴리오 URL 하나가 있어야 합니다.

누군가 “포트폴리오를 보내주시겠어요?”라고 했을 때 PDF 파일을 찾는 대신 링크 하나를 보낼 수 있는 상태입니다. 그리고 프로젝트가 하나 더 생겼을 때 다른 사람에게 부탁하지 않고 직접 내용을 수정하고 다시 공개할 수 있었으면 합니다.

이 책이 목표로 하는 건 바로 그 정도입니다.

개발자가 되는 것이 목표는 아닙니다

이 책에서는 HTML, CSS, JavaScript 문법을 처음부터 가르치지 않습니다. React를 깊게 공부하지도 않습니다. 개발 이론을 배우는 책도 아닙니다.

나중에 더 공부하고 싶다면 그때 깊게 들어가도 됩니다. 지금 우리의 목표는 개발 공부가 아니라 첫 번째 결과물을 완성하는 것입니다.

이런 분에게 가장 잘 맞습니다

  • 실무 경험과 프로젝트는 있지만 PDF나 문서 형태로만 정리해두었던 기획자
  • Figma는 사용할 수 있지만 실제 웹사이트 구현과 배포까지 직접 해본 경험은 없는 디자이너
  • 개인 프로젝트와 경험을 자신의 웹사이트로 보여주고 싶은 취업 준비자
  • 경력은 많지만 무엇을 골라 포트폴리오로 보여줘야 할지 막막한 이직 준비자
  • 의뢰를 받을 수 있는 개인 웹사이트를 직접 만들고 싶은 프리랜서 준비자

공통점은 하나입니다.

보여줄 것은 있는데, 웹사이트로 만드는 방법은 모르는 사람.

이 책은 그런 분들을 위한 책입니다.

AI를 한 번이라도 사용해봤다면 충분합니다

ChatGPT와 대화를 몇 번 해봤다면 시작할 수 있습니다. 코딩 경험은 없어도 됩니다. GitHub를 처음 사용해도 괜찮습니다. Cursor를 처음 열었을 때 코드가 가득 보여도 괜찮습니다.

저 역시 처음부터 개발 용어와 구조를 모두 이해하고 시작한 것이 아닙니다. 만들다 보니 하나씩 알게 됐습니다.

이 책에서도 같은 방식으로 진행합니다.

먼저 만들어보고, 필요한 개념은 그때 이해합니다.

이 책에서는 이런 순서로 만듭니다

STEP 1. 기획 — 포트폴리오의 목적과 보여줄 경험을 정합니다.

STEP 2. 카피 — 내 경력과 프로젝트를 웹사이트에 들어갈 문장으로 바꿉니다.

STEP 3. UI — 사이트 구조와 디자인 방향을 정합니다. Figma와 Stitch는 선택 도구입니다.

STEP 4. AI 코딩 — Cursor에게 개발 작업을 요청하고 결과를 직접 확인합니다.

STEP 5. QA — 브라우저에서 실제 화면과 동작을 확인하고, AI가 확인한 범위와 확인하지 못한 범위를 구분합니다.

STEP 6. 배포 — GitHub에 정상 상태를 저장하고 Vercel을 이용해 실제 URL로 공개합니다.

결국 기획 → 카피 → UI → AI 코딩 → QA → 배포의 전체 사이클을 한 번 경험하게 됩니다.

이 책을 읽는 가장 좋은 방법

처음부터 끝까지 먼저 읽고 나중에 만들어도 되지만, 저는 그렇게 하는 것을 추천하지 않습니다.

가능하면 책을 읽으면서 바로 자신의 내용을 작성해보세요. 프로젝트를 정리하는 장을 읽었다면 내 프로젝트를 실제로 적습니다. Hero 문장을 만드는 장에서는 내 문장을 작성합니다. Cursor 단계에서는 실제로 Cursor를 열어봅니다. 배포 장에 도착했을 때는 실제로 사이트를 공개합니다.

각 장을 시작할 때는 가능하면 “이 장을 끝내면 남는 것”을 먼저 확인하세요.

원고를 읽는 것보다 실제 결과물이 한 단계씩 쌓이는 것이 이 책의 기준입니다.

처음부터 완벽한 사이트를 만들려고 하지 마세요

처음 AI로 웹사이트를 만들면 욕심이 생깁니다. 멋진 애니메이션도 넣고 싶고, 다크모드도 넣고 싶고, 문의폼도 만들고 싶고, 관리자 페이지도 있으면 좋을 것 같습니다.

먼저 가장 작은 완성본을 만듭니다.

Hero, About, Projects, Experience, Contact. 이 정도만 있어도 포트폴리오는 충분히 완성할 수 있습니다. 완성하고 배포한 뒤 필요해지면 그때 확장합니다.

AI가 만든 결과가 마음에 안 들어도 정상입니다

AI에게 한번 요청했는데 완벽한 결과가 나오지 않았다고 실망하지 않아도 됩니다. 저도 거의 항상 수정했습니다.

첫 결과는 너무 화려하기도 했고, 제가 원하지 않은 카드가 추가되기도 했고, 모바일에서 깨지기도 했습니다. 한 부분을 수정했더니 다른 영역이 바뀐 적도 있습니다.

AI 웹 제작은 한 번의 완벽한 프롬프트를 찾는 과정이 아닙니다.

오히려 만들기 → 보기 → 문제 찾기 → 다시 설명하기 → 수정하기를 반복하는 과정에 가깝습니다.

  • 모바일 화면을 수정해봤다.

이것만 준비하고 시작하세요

이 책은 개발을 공부한 뒤 웹사이트를 만드는 방식으로 진행하지 않습니다.

개발 작업의 상당 부분은 Cursor에게 맡기고, 독자는 세 가지를 반복합니다.

무엇을 만들지 정하기→Cursor에게 정확히 요청하기→결과를 직접 확인하기

이 책의 기본 제작 경로

ChatGPT→(Figma / Stitch 선택)→Cursor→React + Vite + JavaScript→GitHub→Vercel

Figma와 Stitch는 선택입니다. 디자인 도구를 사용하지 않는다면 4장에서 정한 IA와 5장에서 정한 문구·컬러·참고 화면을 그대로 Cursor에게 전달하면 됩니다.

왜 React + Vite + JavaScript인가요?

React로 웹사이트를 만드는 방법은 여러 가지가 있습니다. 이 책에서는 로그인·결제·복잡한 서버 기능이 없는 개인 포트폴리오를 빠르게 실습하기 위해 React + Vite를 사용합니다.

언어는 JavaScript로 통일합니다. TypeScript가 나쁜 기술이라서가 아니라, 첫 실습에서 초보자가 신경 써야 할 설정과 오류 메시지를 줄이기 위한 선택입니다. 포트폴리오를 한 번 완성한 뒤 필요하다면 그때 TypeScript를 검토해도 늦지 않습니다.

이 책은 프레임워크를 비교하는 책이 아니므로, 다른 구성 방식은 “이런 선택지도 있다” 정도로만 알아두면 충분합니다.

도구·기능·요금제 확인 기준일: 2026년 10월 1일

  • 운영체제: Windows 중심 (Mac 사용자를 위한 안내는 6장 앞부분에 한 번 정리합니다)

  • AI 코딩: Cursor
  • 코드 저장: GitHub
  • 배포: Vercel
  • 디자인: Figma / Stitch 선택

Cursor, GitHub, Vercel, Figma 같은 서비스는 업데이트가 잦습니다. 메뉴 이름과 버튼 위치는 책과 달라질 수 있습니다. 그래서 이 책은 버튼 위치보다 무엇을 해야 하는지, 무엇이 정상 결과인지, 무엇을 확인해야 하는지를 기준으로 설명합니다.

S의 포트폴리오 · 학습용으로 재구성한 사례

이 책에는 서비스 기획자 S의 포트폴리오가 처음부터 끝까지 등장합니다. S는 저자의 실제 제작 과정을 학습용으로 재구성한 인물입니다. 회사명, 성과 수치, 일정 같은 구체적인 정보는 새로 만들지 않고 공개 가능한 흐름만 사용합니다.

시작 시점의 S에게는 자료가 없지 않았습니다. 이력서에는 회사와 업무가 있었고, 포트폴리오 PDF에는 화면이 있었고, 프로젝트마다 IA·정책·User Flow 문서가 따로 있었습니다. 부족했던 것은 “누구에게 무엇을 먼저 보여줄 것인가”라는 기준이었습니다.

이 장에서 S가 정한 것은 단 두 가지입니다. 가장 먼저 볼 사람은 채용 담당자와 함께 일할 팀이고, 사이트를 본 뒤의 행동은 “연락하기” 하나입니다.

처음 포트폴리오를 만들려고 했을 때 가장 어려웠던 것은 코딩이 아니었습니다. 이미 해온 프로젝트도 있었고, 문서도 있었고, 화면도 있었습니다. 그런데 막상 “웹사이트에서 무엇을 먼저 보여줄 것인가?”라는 질문 앞에서는 쉽게 답이 나오지 않았습니다.

저는 서비스 기획자로 일하면서 IA, 정책, 사용자 흐름, 화면설계처럼 ‘무엇을 만들지’를 정리하는 일을 해왔습니다. 디자인과 개발은 다른 사람의 영역이라고 생각했습니다.

그러다 ChatGPT로 구조와 문장을 정리하고, Figma와 Stitch로 화면 방향을 잡고, Cursor로 실제 구현을 시도하면서 경계가 달라졌습니다.

처음에는 AI에게 “포트폴리오 사이트를 세련되게 만들어줘”라고 요청했습니다. 결과는 빨리 나왔지만 제 사이트 같지 않았습니다. 불필요한 카드와 그래프가 생기고, 제가 강조하고 싶은 프로젝트보다 AI가 보기 좋은 요소가 먼저 배치됐습니다.

그때부터 요청 방식을 바꿨습니다.

  • Hero에는 내 직무와 한 문장 소개만 보여주세요.
  • 기존 Projects 섹션은 유지하고 카드 간격만 넓혀주세요.
  • 모바일에서 제목이 세 줄로 깨집니다. 데스크톱은 유지하고 모바일만 수정해주세요.

이렇게 바꾸자 결과가 달라졌습니다.

AI를 잘 쓰는 능력은 멋진 프롬프트 한 줄을 만드는 능력이라기보다 현재 문제가 무엇인지 보고 작은 단위로 설명하는 능력에 가까웠습니다.

포트폴리오는 비개발자가 AI 제작을 처음 경험하기 좋은 프로젝트입니다. 로그인, 결제, 복잡한 데이터베이스가 없어도 됩니다. 대신 기획, 콘텐츠, UI, 반응형, 배포까지 웹 제작의 전체 과정을 경험할 수 있습니다.

이미지 파일 이름은 사소해 보이지만 배포 오류의 흔한 원인입니다. 내 컴퓨터(Windows)에서는 대소문자가 달라도 열리던 이미지가 Vercel 배포 후에는 보이지 않을 수 있기 때문입니다.

  • 알아보기 쉬운 이름으로 짓습니다.
  • 공백 대신 - 또는 _를 사용합니다.
  • 영문 소문자 중심으로 씁니다.
  • 코드에 적은 이름과 대소문자까지 똑같이 맞춥니다.
  • 같은 이름의 파일을 만들지 않습니다.
  • 너무 큰 이미지는 웹용 크기로 줄입니다.

Cursor로 첫 웹사이트 만들기

비개발자를 위한 AI 코딩 시작법

먼저 확인하세요 — 이 책의 화면 예시는 Windows 기준입니다

이 책의 Cursor 설치, 폴더 열기, 터미널 화면 등은 Windows 환경을 기준으로 설명합니다.

Mac에서도 전체 작업 흐름은 같습니다. 다만 다음은 다르게 보일 수 있습니다.

  • 폴더 경로
  • 설치 화면
  • 키보드 단축키
  • 터미널(Terminal — 명령을 실행하고 개발 서버 상태를 확인하는 창) 기본 환경
  • 파일 탐색 방식

Mac 사용자는 화면이 다르더라도 당황하지 않아도 됩니다. Windows/Mac 안내는 이 책에서 여기 한 번만 정리합니다. 필요한 경우 Cursor에게 이렇게 요청하세요.

PROMPT

내 운영체제를 먼저 확인하고, 지금 환경에 맞는 방법만 안내해줘.

Windows와 Mac 방법을 동시에 설명하지 말고 내가 사용하는 운영체제 기준으로 한 단계씩 안내해줘.

이 책에서 중요한 것은 운영체제별 명령어를 외우는 것이 아니라 프로젝트가 정상적으로 실행되고, 내가 그 결과를 확인할 수 있는 상태를 만드는 것입니다.

이 장을 끝내면 남는 것

  • 실행되는 React 사이트 (브라우저에서 열리는 첫 포트폴리오 화면)
  • GitHub에 저장된 첫 정상 상태
  • Header + Hero 완료 커밋
  • 다음 날 혼자 다시 실행할 수 있는 상태

0장에서 정한 기준대로, 이 장의 모든 실습은 같은 순서로 진행합니다.

  1. 내가 할 일
  2. Cursor에게 요청할 프롬프트
  3. Cursor가 할 일
  4. 내가 확인할 것
  5. 안 됐을 때 전달할 내용

6장은 이 책에서 가장 난도가 높은 장입니다. 한 번에 끝내지 않아도 됩니다. 중간에 세 번의 CHECKPOINT가 있으니, 하루에 CHECKPOINT 하나씩 진행해도 충분합니다.

STEP 1작업 폴더를 만들고 Cursor에서 엽니다

내 컴퓨터에서 포트폴리오 작업용 빈 폴더를 하나 만듭니다.

예: my-portfolio

Cursor에서 이 폴더를 엽니다.

확인할 것

  • 지금 Cursor가 내가 만든 폴더를 열고 있는가?
  • 다른 회사 프로젝트나 개인 파일이 들어 있는 폴더가 아닌가?

STEP 2개발 환경을 Cursor에게 확인시킵니다

PROMPT

나는 개발을 모르는 초보자야.

현재 열려 있는 폴더에 React + Vite + JavaScript 기반 개인 포트폴리오를 만들려고 해.

아직 프로젝트를 만들지 말고 필요한 개발 환경이 준비되어 있는지 먼저 확인해줘.

운영체제, Node.js, npm, Git 설치 여부와 현재 버전이 최신 Vite 요구사항과 호환되는지 확인하고

1. 준비된 것

2. 설치가 필요한 것

3. 내가 직접 해야 하는 것

으로 나눠 설명해줘.

필요한 설치가 있다면 한 단계씩 안내하고 정상 여부까지 확인해줘.

임의로 다른 프레임워크나 개발 방식으로 바꾸지 마.

정상 결과

  • Cursor가 현재 준비 상태를 알려준다.
  • 필요한 도구가 없으면 설치 방법을 안내한다.
  • 준비가 끝나면 다음 단계로 넘어갈 수 있다고 알려준다.

STEP 3React + Vite + JavaScript 프로젝트를 만듭니다

PROMPT

현재 열려 있는 폴더에 React + Vite + JavaScript 기반 개인 포트폴리오 프로젝트를 만들어줘. TypeScript는 사용하지 마.

조건

• 초보자가 관리하기 쉬운 구조

• 불필요한 라이브러리는 설치하지 않기

• 백엔드, 데이터베이스, 로그인, 결제 기능은 만들지 않기

• 필요한 명령은 네가 터미널에서 실행하기

• 실패하면 임의로 우회하지 말고 원인을 먼저 설명하기

프로젝트 생성이 끝나면

1. 어떤 파일과 폴더가 만들어졌는지

2. 사이트를 어떻게 실행하는지

3. 브라우저에서 어떤 주소를 열어야 하는지

를 비개발자가 이해할 수 있게 설명해줘.

여기서 TypeScript를 쓰지 않도록 요청하는 이유는 0장에서 설명한 것처럼 첫 실습의 복잡성을 줄이기 위해서입니다. 프로젝트 생성 후 파일 이름이 .jsx로 끝나면 JavaScript 기준으로 만들어진 것입니다.

정상 결과

  • 프로젝트 파일이 생긴다.
  • Cursor가 사이트를 실행한다.
  • 터미널에 Local 주소가 표시된다.

포트 번호는 컴퓨터마다 달라질 수 있으므로 책에 적힌 숫자를 외우지 않습니다. Cursor 터미널에 표시된 Local 주소를 사용합니다. 이렇게 내 컴퓨터에서 사이트를 띄워주는 프로그램을 Dev Server(개발 서버)라고 부릅니다.

STEP 4브라우저에서 첫 화면을 확인합니다

PROMPT

현재 프로젝트를 실행해줘.

실행 후 브라우저에서 열어야 할 주소를 알려줘.

정상 실행 여부도 확인해줘.

오류가 있으면 바로 수정하지 말고 원인부터 설명해줘.

내가 확인할 것

  • 브라우저에서 화면이 열린다.
  • 새로고침해도 화면이 유지된다.
  • 터미널에 치명적인 Error가 반복되지 않는다.

빨간 글자가 보인다고 모두 같은 문제는 아닙니다.

  • Terminal — 프로젝트 실행 상태와 명령 결과
  • Browser Console — 브라우저에서 발생한 오류
  • Error — 정상 실행을 막을 수 있는 문제
  • Warning — 바로 실패는 아니지만 확인할 필요가 있는 안내

잘 모르겠다면 이렇게 요청합니다.

PROMPT

지금 보이는 메시지 중 내가 먼저 해결해야 하는 Error가 있는지 구분해줘.

Warning과 Error를 나누고, 가장 먼저 확인해야 할 것 하나만 비개발자가 이해할 수 있게 설명해줘.

CHECKPOINT 1

프로젝트가 브라우저에서 정상 실행됐다.

여기까지 됐다면 첫 개발 실행에 성공한 것입니다. 오늘은 여기서 멈춰도 괜찮습니다.

STEP 5첫 문구를 바꿔봅니다

PROMPT

현재 기본 시작 화면을 유지한 채 첫 화면의 주요 제목만

“안녕하세요, [직무] [이름]입니다”

로 바꿔줘.

이번 요청에서는 다른 기능이나 새로운 섹션을 추가하지 마.

수정 후 브라우저에서 변경 내용이 반영됐는지 확인할 방법도 알려줘.

이 단계의 목적은 간단합니다. AI가 파일을 수정했고, 내가 브라우저에서 그 결과를 확인할 수 있다는 경험을 만드는 것입니다.

STEP 6첫 정상 상태를 GitHub에 저장합니다

아직 GitHub 저장소가 없다면 먼저 GitHub에서 빈 Repository를 하나 만듭니다.

이 책의 예시는 다음처럼 진행합니다.

  • Repository name: my-portfolio
  • Visibility: Public 또는 Private 중 선택
  • Add a README file: 체크하지 않음
  • Add .gitignore: 선택하지 않음
  • Choose a license: 필요하지 않다면 선택하지 않음

이 책에서는 이미 Cursor에서 로컬 프로젝트를 만들었기 때문에 GitHub에서는 빈 저장소를 만든 뒤 현재 로컬 프로젝트를 연결합니다.

공개 여부는 자신의 상황에 맞게 선택합니다. 웹사이트를 공개한다고 해서 소스 저장소까지 반드시 공개해야 하는 것은 아닙니다.

GitHub에서 Repository를 만든 뒤 저장소 주소를 준비하고 Cursor에게 전달합니다.

PROMPT

현재 화면이 정상적으로 동작하는지 먼저 확인해줘.

문제가 없다면 이 프로젝트를 Git으로 관리할 준비를 하고, 내가 만든 GitHub Repository와 연결해줘.

나는 Git을 모르기 때문에

1. 현재 변경된 파일

2. Git에 포함되면 안 되는 파일

3. 첫 커밋 메시지

4. GitHub에 푸시할 준비 상태

를 먼저 알려줘.

문제가 없다면 첫 정상 상태를 커밋하고 GitHub에 푸시해줘.

로그인이나 권한 승인처럼 내가 직접 해야 하는 일이 나오면 그 단계에서 멈추고 무엇을 해야 하는지 설명해줘.

완료 후 GitHub에서 무엇을 확인하면 되는지도 알려줘.

여기서 기억할 것

  • Commit — 지금 잘 되는 상태에 이름표를 붙이는 것
  • Push — 그 상태를 GitHub에도 보관하는 것
CHECKPOINT 2

GitHub에 첫 Commit + Push가 올라갔다.

여기까지 됐다면 안전 저장까지 완료한 것입니다. 이후 무엇이 잘못되더라도 돌아갈 기준점이 생겼습니다.

어떤 주소를 공유해야 하나요?

Vercel은 배포할 때마다 그 배포만의 고유 URL을 만들 수 있습니다. 그래서 대시보드에 비슷한 주소가 여러 개 보입니다.

  1. 도구보다 목적을 먼저 정한다.
  2. 가장 작은 완성 범위를 만든다.
  3. AI가 했다고 말한 것보다 직접 확인한 결과를 믿는다.
  4. 문제는 작은 단위로 나눈다.
  5. 정상 상태는 Commit + Push로 남긴다.
  6. 새 기능보다 불필요한 것을 먼저 줄인다.
  7. 공개 후 수정하고 다시 배포하는 경험까지 해본다.

14상세 페이지 새로고침 404

확인SPA routing 설정.
요청“직접 URL 접근이나 새로고침 시 404가 발생해. 이 프로젝트가 SPA인지 확인하고, Vercel rewrite 설정이 필요하다면 이유와 변경 파일을 먼저 설명해줘. 내 승인 전에는 설정 파일을 추가하지 마.”

15메뉴 링크가 안 움직임

확인href / id.
요청“Navigation href와 section id가 일치하는지 확인해줘.”

16Fixed Header 때문에 섹션 제목이 가림

확인scroll offset.
요청“Header 높이만큼 anchor 위치를 보정해줘.”

17모바일 메뉴가 안 닫힘

확인상태 업데이트.
요청“메뉴 클릭 후 모바일 Navigation이 자동으로 닫히게 해줘.”

18Back to Top이 항상 보임

확인scroll trigger.
요청“상단에서는 숨기고 일정 스크롤 이후에만 표시해줘.”

19애니메이션이 과함

확인duration / transform / 반복.
요청“핵심 콘텐츠는 즉시 보이고 장식 모션만 최소화해줘.”

20스크롤할 때 버벅임

확인과한 애니메이션, 큰 이미지, 이벤트 처리.
요청“스크롤 성능 저하 원인을 먼저 찾아줘. 시각 디자인은 유지하고 성능에 영향을 주는 부분만 알려줘.”

21글자가 너무 작음

확인body font-size / line-height.
요청“본문 가독성을 위해 본문 크기와 행간을 점검해줘. 제목 크기는 변경하지 마.”

22사이트가 전체적으로 통일감이 없음

확인spacing / heading / button / radius / width.
요청“새 디자인을 만들지 말고 디자인 시스템이 서로 다른 부분만 목록으로 정리해줘.”

23AI가 같은 수정을 반복해도 실패함

가능한 원인결과 기준이 모호함 / 잘못된 파일을 보고 있음 / 다른 실행 주소를 확인 중임 / 개발 서버 상태가 오래됨 / 원인 진단 자체가 틀림.
요청“같은 수정이 반복해서 실패하고 있어. 코드를 더 바꾸지 말고, 현재 실행 주소·실제 화면을 만드는 파일·최근 변경 반영 여부·가능한 원인을 다시 확인해줘. 확인되지 않은 원인을 사실처럼 단정하지 마.”

24수정할수록 더 망가짐

확인최근 변경.
요청“직전 변경에서 무엇이 바뀌었는지 목록으로 보여줘. 아직 추가 수정하지 마.”

27AI가 프로젝트 구조를 통째로 재편하려고 함
