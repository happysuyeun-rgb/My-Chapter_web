## 0. Count Method

설계본 `books/내 포트폴리오, AI로 직접 만들기/book.html`은 여러 블록을 **한 줄에 압축**해 둔 구간이 있다 (차례 전체, prompt-body, flow, wire, fill, part-list).

- **한 요소가 한 줄인 패턴**: ripgrep 매칭 줄 수 = 출현 횟수.
- **한 줄에 자식이 여러 개인 패턴**: 해당 줄을 직접 읽어 자식 출현을 센다. 아래에 `compacted`로 표시.
- `<p>` 총 태그 수는 prompt-body가 한 줄에 `<p>`를 여러 개 넣으므로, 줄 수(576)보다 **실제 태그가 더 많다**. 정확한 총 `<p>` 개수는 이번 검색만으로는 UNKNOWN.

세 대상(설계본 / Template / Import)은 섞지 않는다.

## 1. Executive Summary

검증된 168쪽 설계본의 표현력은 `book.html` 클래스 계약 + `book.css`다. 같은 계약이 `_template/book.css`에도 이미 들어 있다. 다만 Template HTML과 Import 출력은 그 계약의 **일부만** 쓴다.

`blocks.mjs`가 삽입하는 타입(p / h2 / h3 / ul / ol / checklist / prompt / image / table)은 본문 글의 상당 부분을 만들 수 있다. 설계본을 설계본으로 만드는 상자·STEP·flow·wire·kv·워크시트·엔트리는 **모른다**.

`htmltree.mjs`는 별도 JSON Content Model이 아니다. 원본 문자열 위의 **위치 보존 오버레이**다. HTML → tree → (슬라이스 패치) → HTML은 손실이 없다. tree를 직렬화해 HTML을 다시 만들면 손실이 생긴다.

**결정 (이번 B):**

| 질문 | 결정 |
|---|---|
| 1. 현재 HTML을 계속 원본으로 쓸 것인가 | **YES.** `book.html`이 Content Source of Truth. |
| 2. Structured HTML / htmltree / blocks를 발전시킬 것인가 | **YES, overlay로.** SoT를 바꾸지 않고 타입 커버리지만 넓힌다. |
| 3. 별도 Structured Book JSON을 도입할 것인가 | **NO, 지금은.** 168쪽을 손실 없이 담으려면 스키마가 HTML과 같아지고, 이득이 없다. |
| 4. Legacy HTML과 신규 구조를 공존시킬 것인가 | **형식 플래그는 불필요.** HTML 한 원본 + 파생 조작 층. 168쪽 책은 변환하지 않는다. |
| 5. Practical / Minimal Theme을 기존 엔진 위에 얹을 수 있는가 | **대부분 CSS_ONLY.** 클래스 계약을 유지하면 Paged.js/뷰어를 바꾸지 않고 토큰을 갈아끼울 수 있다. |

권고 경로는 **Option A(HTML SoT) + Option B(htmltree/blocks overlay 확장)** 이다. Option C는 기각한다.

## 5. Semantic vs Presentation

목표는 “Content Model에 남을 것”과 “Theme/CSS에 남을 것”을 가르는 것이다.

### 5.1 SEMANTIC_CONTENT — 모델에 남아야 하는 것

의미가 바뀌면 책이 다른 책이 된다.

- 면 종류: cover / titlepage / colophon / toc / part / chapter-pro / chapter-ch / chapter-ap / chapter-epi
- 장 제목 구조: opener 텍스트 (label, num, h1, sub)
- 본문: p, quote, key, label, strong, mark
- 제목 역할: h2 / h3 / h4 / h5 및 step / case / term / entry
- 목록: ul / ol / checklist
- 상자 **종류**: prompt / result / case / tip / checkpoint / option
- 도식: flow(+chip 텍스트) / wire(+label/line 텍스트)
- 그림: figure + figcaption + slot id
- 표, kv, fill-row 질문, blank, aside.note
- 표지 kicker / 속표지 부제 / 판권 필드

`prompt`는 “파란 상자”가 아니다. 검은 머리 + 본문 + `mark` 치환 자리인 **프롬프트 블록**이다.  
`result-box`는 어두운 스타일이지만 반복 라벨(“이 장을 끝내면 남는 것”)로 **장 성과**를 뜻한다.  
`checklist`의 “CHECK” 글자는 CSS `::before`라서, 스타일을 끄면 라벨이 사라진다. 의미는 `ul.checklist` 클래스에 있다.

### 5.2 STRUCTURAL_LAYOUT — 면/뼈대. 모델 또는 HTML 골격

- `section.*` 순서와 id (`c01`, `part1`)
- opener / part-inner / prompt-tag+body / box+box-label / figure.shot
- TOC 링크 href ↔ section id
- cover-art 스택, 페이지 나눔(`break-before`)

Theme이 이 골격을 지우면 Paged.js 면 구성이 무너진다.

### 5.3 PRESENTATION_ONLY — Theme/CSS

- 색, 글꼴, 크기, 행간, 여백, 모서리
- `cover-grid`, `cover-rule`, chip 흰 배경, `arr` 화살표 색
- `h3::before` 점, `p.key::before` 바, `prompt-tag::after "COPY & EDIT"`, `checklist::before "CHECK"`, `option-box`의 “OPTIONAL · ”
- `@page` 머리글/쪽번호 스타일
- `strong`의 그라데이션 하이라이트

이 항목은 Content Model에 넣지 않는다.

### 5.4 RUNTIME_STATE

- `data-eid` / `data-etag` — 서빙 시에만

## 8. Gap Between A / B / C

```text
Import 본문     ⊂  Template HTML 샘플  ⊂  Template CSS 계약  =  설계본 CSS 계약
                                                      ↑
```

|---|---|---|---|
| 장/부/차례 골격 | YES | YES | YES |

## 10. htmltree.mjs Evaluation

실체: 원본 문자열을 복사하지 않는 위치 트리 (`start/innerStart/innerEnd/end`, parent/children, `attrsRaw`).  
사용처: `blocks.mjs`, `toc.mjs` (`readStructure` / `structureOp` / `syncTocTitles` / `renumber`).

브라우저 DOM AST가 아니다. JSON 문서도 아니다.

| 능력 | 판정 | 근거 |
|---|---|---|
| Node type | YES | `tag` (하이픈 커스텀 태그 포함 → `image-slot`) |
| parent/child | YES | `parent`, `children` (요소만. 텍스트 노드는 자식이 아님) |
| ordering | YES | `children` 배열 + start 오프셋 |
| nesting | YES | 닫는 태그 매칭. RAW/VOID 처리 |
| attributes | YES | `attr()`, `attrsRaw` 원문 |
| classes | YES | `classes()` / `hasClass()` |
| data-eid | N/A on disk | 원본에 없음. 트리는 주입된 HTML도 파싱 가능 |
| text | YES via slice | `inner`/`text`/`stripTags`. 트리 자체는 텍스트 노드 없음 |
| inline markup | YES as elements | `strong`/`mark`는 자식 요소. 재직렬화하지 않으면 보존 |
| custom structure | YES as generic elements | prompt/flow/wire를 특별 취급하지 않음. 그래서 파괴도 안 함 |

### 10.1 Questions

1. **HTML 의미 구조를 충분히 보존하는가?**  
   오버레이로 쓰면 YES. 직렬화 소스로 쓰면 NO (텍스트 노드·공백·주석·속성 따옴표 손실).

2. **Editor에서 안전하게 조작 가능한가?**  
   현재 용도(뒤에서 splice)로는 YES. 표지/오프너는 블록 도구가 막고, 장 구조는 `toc.mjs`가 클래스 계약으로 다룬다. 위험: `scanEditable`과 tree 위치가 어긋나면 409.

3. **Theme 변경 시 활용 가능한가?**  
   클래스 읽기에는 YES. 토큰 저장소는 아님. Theme은 CSS가 한다.

4. **AI Editing 입력 모델로 활용 가능한가?**  
   부분. 개요(`outlineOf`)와 오프셋 패치는 가능. 트리 전체를 프롬프트에 넣기엔 오프셋이 크고 불안정하다. AI가 만져야 하는 것은 클래스 계약이 있는 HTML 조각이 더 안전하다.

5. **Supabase/DB 저장에 적합한가?**  
   NO. 오프셋은 파일 버전에 묶인다. 저장하려면 HTML 문자열(또는 별도 스키마)이 필요하다. 지금은 DB가 없다 (M0.5-A).

6. **Versioning 가능한가?**  
   트리 자체는 NO. 버전은 이미 HTML sha1 (`editable.versionOf`). History는 전체 HTML 스냅샷.

7. **HTML → Tree → HTML round-trip 손실?**  
   트리를 **만들지 않고** 원본을 슬라이스하면 LOSSLESS.  
   트리에서 HTML을 다시 쓰면 LOSSY.

**역할 판정:** htmltree는 “Structured Content Layer 대용 JSON”이 아니라 **안전한 HTML 수술 도구**다. 지금 단계에서 별도 JSON Model을 대신할 수 있다. 단, 제품 스키마로 승격하지 않는다.

## 11. Round-trip Risk (Conceptual — No Code Written)

### A. 현재 HTML → htmltree → HTML

방식: parse 후 `outer`/`applyEdits`로 원본 슬라이스.

| 항목 | 판정 |
|---|---|
| Text / Inline mark / Lists / Nested markup | LOSSLESS |
| Classes / Attributes / data-eid | LOSSLESS (eid는 원본에 없음) |
| Image slot / Table / Prompt / Checklist | LOSSLESS |
| STEP / Flow / Wire / Chapter opener | LOSSLESS |
| Page structure / Cover / TOC / Appendix | LOSSLESS |

**판정: LOSSLESS** — 트리를 직렬화하지 않는 현재 사용법 기준.

### B. 현재 HTML → Block Model → HTML

방식: 설계본을 `BLOCK_TYPES`로만 다시 펼친다고 가정.

| 항목 | 판정 |
|---|---|
| Text (일반 p) | MOSTLY LOSSLESS |
| Inline mark | LOSSY (`retype`/새 p는 mark를 모름. 기존 inner 패치는 유지) |
| Lists / checklist / prompt / image / table | MOSTLY LOSSLESS (아는 타입만) |
| Nested markup in unknown units | UNKNOWN~LOSSY |
| Classes on p/h2/h3 | LOSSY (`retype`이 클래스 제거) |
| Attributes | LOSSY (id만 일부 유지) |
| data-eid | N/A (재주입) |
| STEP / Flow / Wire / boxes / kv / fill / entry / term / case | LOSSY (타입 없음 → 평문 h/p로 붕괴) |
| Chapter opener / Cover / TOC / Appendix / Part | LOSSY (블록 모델 범위 밖. structure 층은 별도) |

**판정: LOSSY** — 168쪽을 Block Model이 SoT가 되면 설계가 죽는다.

### C. 현재 HTML → 신규 JSON Model → HTML

스키마가 설계본 전 패턴 + 인라인 + 슬롯 + TOC 링크 + 표지 장식 + CSS 클래스 계약을 **전부** 복제하지 않으면:

| 항목 | 판정 |
|---|---|
| 위 B에서 아는 것 | 스키마를 잘 만들면 MOSTLY LOSSLESS |
| 설계 전용 패턴 | 빠지는 순간 LOSSY |
| 공백·한 줄 압축·잔여 메타(genspark, thumbnail) | LOSSY 또는 UNKNOWN |
| image-slot id / sidecar 키 | 스키마에 명시해야 함 |
| `@page` 제목 문자열 | JSON 밖 (CSS) |

**판정: LOSSY** (완전 스키마를 지금 확정하지 않음). 완전 스키마는 HTML 재기술에 가깝다.

## 12. Theme Engine Feasibility

전제: 클래스 계약은 유지. Practical → Minimal은 **같은 HTML**에 CSS만 바꾸거나 토큰만 바꾸는 것.

`book.css` 현황:

- `:root` 토큰 있음 (`--paper`, `--paper-2`, `--ink`, `--ink-2`, `--ink-3`, `--rule`, `--accent`, `--accent-soft`, `--sans`, `--mono`)
- 인라인 style **0**
- `!important` **0**
- 페이지: `170mm × 240mm`, 여백 `22mm 18mm`
- 본문: 9.6pt / line-height 1.78 / Pretendard
- 하드코딩 잔여: `#fff` (chip, prompt, checkpoint, wire-box, 채운 shot), 표지/부/result의 추가 `oklch`/`rgba`, `@page :left` 책 제목 문자열, 다수 `mm`/`pt`

뷰어(`paged_book_viewer.js`)는 Theme을 모른다. HTML Contract만 로드한다 (M0.5-A §10).

| 영역 | 판정 | 이유 |
|---|---|---|
| body font | CSS_ONLY | `--sans` |
| heading font | CSS_ONLY | `--sans` / `--mono` |
| font size | CSS_ONLY | body 9.6pt, h2/h3 pt |
| line height | CSS_ONLY | 1.78 |
| page margin | CSS_ONLY | `@page` |
| chapter opener | CSS_ONLY (크기·색) / CSS_PLUS_MINOR_MARKUP (번호 숨김 시 빈 공간) | `op-num` 58pt는 CSS. 마크업을 빼면 구조 변경 |

| TOC | CSS_ONLY | 번호는 `target-counter` |
| paragraph | CSS_ONLY | |
| quote / key / label | CSS_ONLY | 클래스 유지 |
| prompt box | CSS_ONLY | |

| result / tip / case / checkpoint / option | CSS_ONLY | 타입 클래스는 유지, 색만 교체 |

**STRUCTURAL_CHANGE_REQUIRED 로 본 영역:** Theme 전환만으로는 없음.  
단, Minimal이 “오프너 번호 마크업 삭제”, “파트 간지 제거”, “프롬프트를 다른 태그로 교체”를 요구하면 STRUCTURAL이다. 그건 Theme이 아니라 다른 책이다.

- result: ink 바닥 + paper 글
- checkpoint: accent 테두리 + 흰 바닥
- table: ink 헤더선, rule 행선
- step-tag: ink 바닥 (h2.step은 accent)
- flow/chip: paper-2 줄, 흰 chip
- wire: dashed ink-3, 흰 box

머리글 책 제목은 지금 CSS 문자열이다. Theme 토큰이 아니라 **책 메타**다. Template은 `{{TITLE_CSS}}`, 설계본은 하드코딩. Theme 엔진과 별개로 빼야 할 값이다.

### OPTION A — HTML Source of Truth 유지

## 15. Dual-Format / Coexistence

M0.5-A는 `legacy_html` vs `structured_v1` 플래그 자리를 `book.json` 후보로만 적고 정하지 않았다.

이번 B 결론:

- **형식 플래그를 지금 넣지 않는다.**
- 모든 현재 책은 이미 같은 HTML 계약이다. “레거시”와 “신규”가 파일 포맷으로 갈리지 않는다.
- 차이는 밀도다. Import 책 = 계약의 부분집합. 설계본 = 계약의 전체.
- 168쪽 책은 변환하지 않는다. `legacy_html`로 낙인찍지 않는다.
- 나중에 파생 JSON이 필요하면 **읽기 전용 뷰**로 뽑는다. 쓰기 SoT는 HTML.

공존이 필요한 지점은 포맷이 아니라 **편집 깊이**다.

- 글 패치: 모든 책
- 블록 팔레트: 아는 타입만
- 구조(장/부): `toc.mjs` 클래스 계약
- 설계 타입: 팔레트가 따라갈 때까지 HTML로 존재

## 16. How Theme Sits on the Existing Engine

구현하지 않는다. 얹는 위치만 정한다.

```text
books/<folder>/book.html     ← 클래스 계약 (Content)
books/<folder>/book.css      ← 지금 책 테마 (Practical 실체)
     또는 공유 tokens + 책 오버라이드
_shared/paged_book_viewer.*  ← 셸만. Theme 모름
Paged.js                     ← @page / break. 유지
```

Practical → Minimal:

1. `:root` 토큰 세트만 교체 (글꼴, 색, 여백, 상자 바닥)
2. 필요하면 컴포넌트 규칙의 `#fff` / 추가 oklch를 토큰으로 승격
3. HTML 클래스·섹션 종류는 그대로
4. 표지 장식을 덜 쓰려면 먼저 `display:none` / 크기 0 (CSS_ONLY). 마크업 삭제는 Theme이 아님
5. `@page :left` 제목은 Theme이 아니라 책 메타로 빼는 편이 맞다

Template CSS가 이미 설계본과 같은 선택자를 쓰므로, 새 책과 설계본에 **같은 Theme 파일을 얹을 수 있다**.

## 17. Recommendation (Answers the Five Questions)

1. **HTML을 계속 원본으로 쓴다.**  
   렌더/편집/히스토리/PDF가 이미 그 문자열을 기준으로 한다.

2. **htmltree / blocks / toc 층을 발전시킨다.**  
   SoT가 아니라 overlay. 설계본 패턴을 `BLOCK_TYPES`에 더하는 것은 미래 구현 과제다. 이번 단계는 구현하지 않는다.

3. **Structured Book JSON은 도입하지 않는다.**  
   지금 도입하면 168쪽을 손실하거나 HTML을 그대로 복제하게 된다.

4. **포맷 공존(legacy vs structured file)은 하지 않는다.**  
   한 HTML 계약, 밀도만 다름. 168쪽은 그대로 둔다.

5. **Theme은 기존 엔진 위 CSS 토큰 층이다.**  
   뷰어·Paged.js·book.html을 교체하지 않는다. Practical/Minimal은 같은 클래스 계약의 두 토큰 세트다.

권고 한 줄: **Option A + B overlay. Option C 기각.**

## 19. Facts Required for Later Phases

1. Content SoT는 `book.html` 문자열이다. JSON으로 바꾸지 않는다.
2. 표현 상한은 설계본 클래스 계약이다. Import가 아니다.
3. Template CSS ≈ 설계본 CSS. Theme 계약은 이미 CSS에 있다.
4. `blocks.mjs` Full insert는 본문 설계 타입의 약 32%. 168쪽 전 패턴이 아니다.
5. `htmltree` round-trip은 오버레이일 때 LOSSLESS, 직렬화면 LOSSY.
6. Block Model을 SoT로 쓰면 LOSSY.
7. 신규 JSON Model은 지금 LOSSY.
8. Theme Practical→Minimal은 클래스 유지 시 거의 CSS_ONLY.
9. 168쪽 책은 변환하지 않는다.
10. 다음 구현이 있더라도 C(JSON SoT)나 React/Supabase/렌더러 교체는 A 사실과 이 B 결정에 반한다.
